# 0.19.0, the second release

0.19.0 is the second published version of the client: a beta for XCP-ng 8.3, marked as a
pre-release, with the same supported part as 0.18.0. It is tag `v0.19.0` at commit
`9d858cceaee3a46c8407f2f45eea8a6068c21b67` on the main branch, published on 2026-11-12 at
<https://github.com/z23/xenadmin-rs/releases/tag/v0.19.0>. The operator decided the
release that day.

What it supports and what in it is experimental is drawn in the
[feature scope](../FEATURES.md); what changed, what is known to be wrong and what was not
verified are in the [changelog](../../CHANGELOG.md), which is also the release's notes. The
[parity ledger](../PARITY-IMPLEMENTATION.md) remains the completion authority, and no
milestone is declared complete by this release.

## Since 0.18.0

Twenty-seven commits. Most of the work is inside the client:

- Host records are read through bindings generated from the API description that
  upstream's generator writes for the toolstack the client is qualified on. They live in
  one crate, `xenadmin-xapi`, under upstream's LGPL 2.1 with its linking exception; the
  rest stays under the MIT licence ([decision](../decisions/0004-generated-bindings.md)).
  The packages carry that crate's licence and notice under `third-party/`.
- Every call and field the core names is checked against the generated catalogue,
  enumeration values are written as generated constants, the number of arguments of the
  calls written out with them is checked, and debug builds can check that each record is
  read as the class it is of. The repository's check runs that over the tests.
- The move found defects that fixtures had hidden, and they were fixed: the pool's
  HTTPS-only setting read from the wrong class, a disk refused as in use because of a
  field hosts do not send, a comparison with a disk type that does not exist, seven
  reads through the wrong class that changed nothing, and a cross-pool refusal reported
  as an invalid response (findings 55 to 62 of the
  [live report](2026-11-09-lab-qualification.md)).
- In the window: a console in a window of its own is drawn at the interface size and
  follows it, the details pane's width is kept between runs, the performance page has
  its margin, and `--version` prints the version and exits.
- The README shows the client on the lab in three pictures.

## Verification

[CI for the commit](https://github.com/z23/xenadmin-rs/actions/runs/43151954265) passed
before the main branch was moved to it. The
[tag's workflow](https://github.com/z23/xenadmin-rs/actions/runs/43154770155) then repeated
the checks on the tagged commit and built the packages: formatting, Clippy with warnings
denied and 1,304 workspace tests (578 core unit with six native suites ignored, 355 direct
protocol, 352 Rune with one measurement ignored, five profile, five bindings, four TLS,
four probe and one of the lab harness's own), the 46 vendored RFB tests, 32 lab tooling
tests and 21 packaging tests, and the headless scenes. The 95 live scenarios are ignored
there by design; they run against the lab.

The packages were checked while the release was still a draft, and it was published only
after that:

- Both were downloaded from the draft and matched their checksum files, on the workstation
  and again inside the virtual machine.
- On an untouched Ubuntu 24.04.5 cloud image with only the documented runtime packages
  added, the archive's installer put release `0.19.0-3fdb49186ceaa589` under `~/.local` and
  reported it active. The installed client answered `--version` with `xenadmin-rs 0.19.0`.
- The archive holds `third-party/xenadmin-xapi-0.19.0/` with the LGPL licence text and the
  notice of the bindings' source.
- The installed desktop rendered three scenes with the software Vulkan driver: the
  synthetic inventory, the console with a typing review pending, whose tree holds the
  typing button, and a host administration dialog, whose tree holds the experimental
  notice. The AppImage, run by extraction, rendered the synthetic inventory to the same
  bytes as the installed build.
- The installed probe logged in read-only through the lab's member with each endpoint
  pinned to its own certificate, the password given on standard input, and listed the lab
  pool with its two hosts and four guests.
- After publication the public release page answered, the public checksum files were the
  ones checked, and the README's three pictures loaded from the public repository page.

The live evidence is in the [live qualification report](2026-11-09-lab-qualification.md),
all of it on XCP-ng 8.3.0 in the disposable lab and gathered from builds of the workspace,
not from these packages. On the code that was released, the 22 scenarios of the supported
part and its failure paths were run again and passed; the operation areas whose reads had
moved onto the generated views were run again earlier that day, on builds of the commits
before it. The report's rows say which is which.

## What this does not show

- Nobody has used the released packages: the checks above were scripted, on one
  distribution, without a display.
- No login through the desktop window and no console were tried from the packages. Those
  paths were exercised from workspace builds of the same source, among them the build
  the README's pictures were taken from.
- Not every lab scenario was run again on the generated bindings before the release. The
  live report lists those still resting on their earlier runs: the control-domain memory
  change, HA with its takeover, the member's certificate reset, the member shutdown and
  power cycle and the storage interface repair.
- The Arch image was not started for this build.
- The packages are not signed. Their checksums detect damage and do not authenticate a
  download.
