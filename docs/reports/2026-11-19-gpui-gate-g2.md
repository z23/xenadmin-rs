# GPUI migration, gate G2 (shell): state on 2026-11-19

Gate G2 of [the migration plan](../GPUI-MIGRATION.md) ("Phase 2: shell"), criterion by criterion,
after the cutover of the code. Each criterion is quoted word for word from the plan and is one of:
**met** (with the test, scene or live evidence that shows it), **partly met** (what is shown and what
is missing) or **not met** (why, and what it needs). This report supersedes
[the report of 2026-11-14](2026-11-14-gpui-gate-g2.md), which described a preview shell that no
longer exists.

**The gate is not passed: criteria 1 and 5 are partly met.** Criteria 2, 3 and 4 are met.

What the words mean here, as everywhere in this project's reports:

- A *test* is a model test of `crates/xenadmin-ui` or a window test of `crates/xenadmin-desktop`
  on GPUI Kit's headless test platform, with real pointer, key and text events and no compositor.
- *Live, headless* is a run of the real shell and core against the project's lab without a window
  ([report](2026-11-19-gpui-live-headless.md)); its evidence directories are under
  `/var/lib/libvirt/images/xenadmin-rs-lab/evidence/gpui/`, outside the repository.
- Nothing of the GPUI front end has run in a real window on a compositor. No criterion below is
  called met on the strength of a planned run.

The checks named were run on 2026-11-19: the whole of `./scripts/check.sh` by the cutover at commit
`581ba08`, and again for these reports (started at `c82bc7c`; documents only differ); see
[the G5 report](2026-11-19-gpui-gate-g5.md), criterion 1, for the result.

## Criteria

### 1. "The GPUI build connects to the lab pool with a pinned certificate and shows live inventory updates."

**Partly met.**

Shown, live and headless: scenario 1 of the live report (`lab_g2_add_server_and_follow_the_host`,
evidence `1795044929-g2-add-server-and-follow`). Add Server with the coordinator's address; the
certificate of each of the two servers inspected, its SHA-256 fingerprint equal to an independent
inspection, the pin refused until the exact endpoint is typed and confirmed, then accepted; Connect;
the tree shows the pool, both servers, the guests and the repositories (`06-connected.png`). A
description changed through a second connection appeared on the General tab 0.2 s later
(`08-general-after-outside-change.png`).

Missing: "the GPUI build" in that run is the application as `app::start` wires it inside the test
process, drawing off screen. The client binary was not run, and nothing was shown in a window on a
compositor. It needs one run of the built client in a real session against the lab.

### 2. "Selection stays on the same object across updates."

**Met.**

- Model test `the_selection_survives_an_inventory_update` (`crates/xenadmin-ui/src/model_tests.rs`).
- Window test `the_selection_stays_on_its_object_across_an_inventory_update`
  (`crates/xenadmin-desktop/tests/shell.rs`), and `a_multi_selection_is_kept_by_id`
  (`tests/renderer.rs`) for a grid.
- Live, headless: in scenario 1 the selection was on the same guest before and after the change
  from outside (`07-general-before.png`, `08-general-after-outside-change.png`).

### 3. "These scenes render through the scene tool: `demo`, `demo` in light theme, `connect`, `connect-insecure`, `large-inventory`, `connections`, `connection-settings`, `connection-trust`, `certificate-review`, `host-version-notice`, `inventory-context`, `general-information`, `search-pools`, `unavailable-actions`, `interface-large`."

**Met.**

All fourteen names are in the scene tool's list (`xenadmin-scenes --list`, 141 scenes: the 129 of the
old front end and twelve fixtures of the renderer, the shell and the kernel). `./scripts/check.sh`
renders every listed scene at 1440 by 900 in the dark theme to a PNG and an element tree under
`artifacts/ui/`, and `demo` again in the light theme (`demo-light.png`); the tool exits with an error
when a frame lacks an element its description has. The window test
`every_scene_renders_with_the_keys_of_its_description` (`tests/renderer.rs`) holds the same for every
registered scene without a graphics adapter. A render shows that a scene draws completely, not that
it matches the picture of the old front end; the pictures were not compared.

### 4. "A keyboard-only interaction test reaches the tree, the tab strip, the grid and a menu command."

**Met**, on the test platform.

Window test `the_keyboard_alone_reaches_the_tree_the_tabs_the_grid_and_a_menu_command`
(`crates/xenadmin-desktop/tests/shell.rs`). Its keys are the Kit's test key events: it establishes
the focus order and the key handling of the interface, not the behaviour of a keyboard on a Wayland
seat.

### 5. "Review finds no action button outside the toolbar, a tab's local action row, or a dialog."

**Partly met.** A test holds it for the shell and the construction of the interface holds it for
commands; the review the criterion names, of the rendered scenes one by one, was not made.

- Window test `no_region_has_an_action_button_of_its_own` (`tests/shell.rs`) covers the shell's own
  regions: title and menu bar, toolbar, navigation pane, object header, tab strip, status bar.
- The body of a tab and every dialog are descriptions made by the model, drawn by one generic
  renderer. A command reaches the interface only through the command table (238 commands; the
  Commands table of [the ledger](../GPUI-MIGRATION-LEDGER.md) gives each one's menu path, toolbar
  slot, context menus and local row). A few controls inside a tab body are buttons of the body and not
  commands, where the ledger's Deviations table says so (for example "Load saved preview" in the
  inspection section of the Snapshots tab). Whether each of those is an action in the plan's sense was
  not reviewed one by one.

## Records the plan asks for at this gate

- Decision D3 (minimum window 800 by 600, navigation pane behind a toggle below 1100) and D4 (tabs
  beyond the reference) stand as the defaults; the operator has not vetoed them. D8 (theme): the Kit's
  tokens with the project's accent, light and dark, with the contrast test
  `controls_are_distinguishable_from_the_surfaces_they_sit_on` (`tests/theme.rs`).
- `large-inventory` frame times ("Performance and accessibility records"): a check that a frame, a
  scroll and a selection change build only the rows in view
  (`the_work_of_a_frame_does_not_grow_with_the_inventory`, `tests/large_inventory.rs`) passes. The
  measurement `measure_large_inventory` was taken once, in a release build on a machine loaded by
  other builds, with the offscreen renderer (p50 / p95 in ms: idle frame 2.4 / 2.9, tree scroll
  4.9 / 6.3, grid scroll 6.7 / 8.1, tree selection 11.5 / 13.2, inventory replaced 23.9 / 25.6, as
  the engineer reported them; they are not in a file of the repository). A record on an idle machine
  is still to be made, and no presented frame on a real surface has been measured.
- Accessibility: the element tree of every scene is stored with its render (`artifacts/ui/*.json`).
  No screen reader has been run.

## Gate G1, for the record

The report of 2026-11-14 for gate G1 described the first extraction of the model. What G1 asked for
holds in the tree today in this form: `cargo tree -p xenadmin-ui` shows no `rune`, `rune-kit` or
`gpui` crate (a guard of `./scripts/check.sh`); the tab matrix tests pass with the model's tests; the
ledger lists every command, every scene and every test of the old front end
(`python3 scripts/gpui_ledger_tables.py check` prints no difference); and no commit of the migration
changes `xenadmin-core`, `xenadmin-xapi` or `xenadmin-process`. The branch does differ from `main` in
`xenadmin-core` and `xenadmin-xapi`, through the merge of the separate branch `xapi-bindings`
(`3b8b4e6`, three commits about typed classes of the API); that work is not part of the migration and
is the only source of the difference (`git log main..HEAD -- crates/xenadmin-core crates/xenadmin-xapi
crates/xenadmin-process`). Its first criterion,
"`./scripts/check.sh` passes with the Rune front end using Tier A", is history: the Rune front end
is removed.
