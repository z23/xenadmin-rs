# Reviewed standalone-host pool joining

Pool policies now offers **Join another pool…** for a writable, current standalone
source connection. The destination must already be connected independently. The review
captures both profiles/pool observations and the exact host/coordinator UUIDs, asks for
the source host UUID, and accepts a transient destination administrator credential.
Switching destination clears entered credentials and confirmation; changed profiles or
connection generations invalidate the review. No keyring load or save is involved.

The core authenticates the supplied destination credential at the existing trusted
endpoint without following a coordinator redirect, verifies the destination pool and
coordinator, and requires a local superuser. Fresh checks require HA disabled on both
pools, a single source host, halted/unscheduled source guests, no active source guest or
host operations, no shared source storage except a tools SR, and no bonds/tunnels.
The destination coordinator must be live, enabled and idle. Remaining compatibility
checks are authoritative XAPI join checks. The client never automatically prepares or
forces a join, stops guests, disables HA, or compensates after partial server work.

Both pools are reserved transactionally against VM and infrastructure operations.
Task cancellation remains the existing narrow recovery exception. The same typed scope
is used for history, cancellation, recheck and acknowledgement. Active malformed or
inconsistent journal payloads block admission rather than being ignored. Secret inputs
and temporary session references are absent from public history and stored journal data.

Success requires a saved synchronous join reply and fresh destination membership equal
to the captured baseline plus the source host. A lost reply stays unknown even if the
host appears. The source connection remains bound to its original pool; its expected
identity transition can interrupt the reply and leave an unknown outcome. Recheck uses
a current destination connection and never repeats the join. Later legitimate changes
to coordinator/address, HA or membership also prevent automatic success verification;
the operator must inspect and explicitly acknowledge any still-uncertain outcome.

## Protocol evidence

The official [pool API](https://xapi-project.github.io/xen-api/classes/pool.html#join)
defines the ordinary synchronous join using destination address, username and password.
The current [upstream implementation](https://github.com/xapi-project/xen-api/blob/master/ocaml/xapi/xapi_pool.ml)
checks HA, standalone membership, guest state, shared storage, bonds, tunnels and other
compatibility requirements. Its `join_common` initially authenticates through a remote
RPC with certificate verification disabled, exchanges pool certificates, then uses
verified pool transport. The desktop's independent connection does not bind that initial
host-to-host bootstrap. The UI states this limitation and requires a trusted management
network; it never claims desktop pins provide end-to-end protection for pool joining.
These sources were inspected on 2026-11-08; source behavior is evidence, not live-host
qualification of any installed XCP-ng build.
