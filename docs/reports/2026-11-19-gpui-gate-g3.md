# GPUI migration, gate G3 (supported core): state on 2026-11-19

Gate G3 of [the migration plan](../GPUI-MIGRATION.md) ("Phase 3: supported core"), criterion by
criterion, after the cutover of the code. Each criterion is quoted word for word from the plan and is
one of: **met**, **partly met** or **not met**, with what shows it and what is missing. This report
supersedes [the report of 2026-11-14](2026-11-14-gpui-gate-g3.md), which described headless previews
that called no host and no longer exist.

**The gate is not passed: criterion 2 is partly met.** Criteria 1 and 3 are met by a run in a
virtual machine with injected input and a software renderer, not by a person at a desk; criterion 4
is met; criterion 5 was met at the last commit that held the Rune build. Of criterion 2, most of the
paths it names are now shown, all of them headless, and a few are still missing. The plan made G3
"the recovery gate on the GPUI build": that run has taken place once, in the virtual machine, with
the AppImage built by CI at commit `e808a2f`. (Brought up to date later on 2026-11-19, after the
runs of that day and the merge of their branches.)

Terms as in [the G2 report](2026-11-19-gpui-gate-g2.md): a *test* runs on the Kit's headless test
platform; *live, headless* is the real shell and core against the lab without a window
([report](2026-11-19-gpui-live-headless.md), evidence directories under
`/var/lib/libvirt/images/xenadmin-rs-lab/evidence/gpui/`); *in a virtual machine with injected
input* is the driven session of [its report](2026-11-19-gpui-vm-session.md): the CI AppImage as a
Wayland client of sway 1.12 on the display of a QEMU machine, software rendering, every key and
pointer event injected at the machine's devices by a script. No person has used the GPUI front end
in a window, and it has not drawn on a hardware GPU.

## Criteria

### 1. "The recovery gate from `README.md`, run with the packaged GPUI AppImage on an empty state directory: with XO shut down, locate the XO VM, start it and use its console."

**Met**, in a virtual machine with injected input and a software renderer.

Shown ([session report](2026-11-19-gpui-vm-session.md), section E; frames 094 to 104 of its
evidence, of which frame 103 was looked at again for this report): the AppImage built by CI at
commit `e808a2f` (run 44436396899; its checksum verified), started on an empty state directory. The
appliance `XOA` had been shut down by another client and Xen Orchestra did not answer. In the
client: Add Server with both pins and the password; `XOA` typed in the navigation search box, which
left the pool and that VM in the tree; the VM selected, shown halted; Start from the toolbar; its
Console tab showed the boot and then `xoa login:`; ten characters typed at the machine's keyboard
appeared at that prompt and were erased again. Nobody logged in to the appliance. The client's
connections, read with `ss` in the machine throughout, went to the coordinator's address only. Xen
Orchestra answered again afterwards.

The criterion's words are satisfied by that run: the packaged AppImage, the empty state directory,
Xen Orchestra shut down, and the three steps, each observed on the machine's display; the words ask
for no person and no graphics card, and the run had neither. What it leaves for a person: the same
on a desk, on the operator's compositor, with a hardware GPU; and with a package that holds the
fixes made since (a held key did not repeat in a console with that AppImage, finding 2 of the session
report). Gate G5, criterion 2, asks for the gate again on the release artifact.

The three host scenarios and the lost member were run once each, at the commits at which they were
written, and not repeated: each restarts, reboots or cuts the power of the member. Nobody looked at
the frames of these fourteen runs; each statement rests on assertions over the model, the element
tree or captured pixels. The clipboard of "Type Clipboard as Keys" was the test platform's own.

Still missing, and named by the criterion or by the supported list of `docs/FEATURES.md`:

- a coordinator change through the front end, and with it maintenance of the coordinator: a handover
  was not started from the front end, and a lost coordinator means cutting the power of the lab's
  coordinator, which the rules for the lab on that day did not allow. The core's own live scenarios
  cover both at the core's level;
- the host's own refusal of an evacuation (it needs a guest that cannot be moved; not produced);
- the accepted path of a forced shutdown during a migration: forbidden on this lab, which it wedged
  twice (finding 63 of the lab report); only the refusal is shown;
- a saved password in the desktop keyring and connection at startup: the headless platform has no
  keyring, the session machine had none, and the operator's keyring is not to be touched;
- an operation in flight while the coordinator's toolstack restarts: the scenario shows that the
  reconnection submitted nothing, not that a pending write is reconciled before it is retried.

The runs of the table were made at commit `e2d4572`. Merged after them: the last round of fixes to
the model and to the renderer (the branches `port/f1` and `port/f2`; 72 source files of the two

then the cutover, which renamed the crate and changed the front end in four more places (where a
group's key sits, a private text area's edit, the Down key after a click in a table with several
selected rows, the order of the Storage tab's row of actions; commit `60785ff`). Every live test was
therefore run again on the tree after the cutover, at commit `56fedbd`, later on 2026-11-19: all
passed at the first attempt, the maintenance scenario again with a real evacuation of one guest
(the live report, "Repeated after the cutover", has the table and the evidence directories). What
the first table shows is shown for the tree after the cutover as well. And every test of the first table was run a third time, passing, on the tree with the day's
branches merged (commit `a6ccb33`), followed by three of the second table's scenarios that act on

clipboard); the live report's section "Repeated on the merged tree" has the evidence directories.
The scenarios that restart, reboot or cut the power of a server were not repeated on that tree.

And all of it was headless: "through the GPUI build" was the application inside a test process. In
a window, the session of criterion 3 covered connecting, a guest started, consoles and a
disconnection, and none of the failure or interruption paths. It needs the missing paths, and a
person's run of the supported paths in a window.

### 3. "One driven desktop session (nested compositor, AT-SPI, physical key injection) covers connections, tables, search, console keyboard input and the host console."

**Met**, in a virtual machine with injected input and a software renderer, with one difference from
the criterion's parenthesis.

Shown ([session report](2026-11-19-gpui-vm-session.md), sections C, D and F), with the AppImage built
by CI at commit `e808a2f` unless said otherwise:

- connections: Add Server through the certificate reviews of both servers, a saved connection after a
  restart (listed disconnected, nothing connecting by itself), Connect without a new review,
  Disconnect;
- tables: a grid sorted both ways, scrolled by the wheel, a row chosen by the pointer and moved by
  the arrow keys, a context menu at the pointer, on the demo and on the lab pool's Search tab;
- search: text typed and pasted into the navigation search box narrowed the tree;
- console keyboard input: a lab guest recorded, from its own input device, the exact test line with
  all US punctuation, the same key codes when the compositor's layout was German, and right-hand
  modifier codes that only the Wayland key-code path of
  [decision 0006](../decisions/0006-console-key-codes.md) (route A) can send. With the CI package a
  held key arrived as one press; with a build of the fix (commit `8d6ec1d`, now merged) the guest
  recorded the repeats;
- the host console: the member's text console drawn, saved through the portal's file chooser, opened
  in a separate window and put in and out of fullscreen. Nobody logged in to a host.

The difference: the compositor was not nested in a desktop. It ran on the display of a virtual
machine with a seat of its own, and the keys were injected at that machine's keyboard device; AT-SPI
was used to find controls and to read state, never to act. The criterion's words are satisfied by
that session: one driven session covered each of the five subjects, with physical key codes passing
a kernel input device, a seat and the Wayland protocol; a compositor on a machine's own display is
not a lesser session than a nested one. What it is not is said in that report's last section: no
person, no hardware GPU, one compositor (sway 1.12, not the operator's Hyprland, GNOME or KDE), no
X11, a virtual keyboard.

The harness of the earlier driven sessions, which finds its elements in the
accessibility tree of the Rune interface, was not rewritten: the session used a driver of its own,
kept outside the repository.

### 4. "Every scene and interaction test of the supported areas is ported."

**Met.**

- Scenes: all 129 scenes of the old front end are registered and render
  ([ledger](../GPUI-MIGRATION-LEDGER.md), Scenes table; `python3 scripts/gpui_ledger_tables.py check`).
- Tests: the ledger gives each of the 371 tests of the old front end its disposition: 154 moved, 119
  ported, 94 split into a model test and a window test, 4 retired with a reason, none open. The row
  that was open when this report was first written, `search_clear_button_empties_the_search_and_restores_every_row`
  (navigation and search), is ported: the window test
  `the_search_box_clear_button_empties_the_search_and_restores_every_row` (`tests/shell.rs`) presses
  the search box's own clear button with pointer events of the test platform.
- The criterion's words are satisfied: every scene is registered and every test has a successor or a
  recorded reason. What "ported" does not say, and the ledger does: the assertions of a successor were not compared with those of the
  test it succeeds; 5 ported rows have no window half although their name promised reachability at a
  window size; no test has a console stream (the canvas with real frames and keys was exercised only
  in the live headless runs), and the Wayland key listener has no test (its key repeat has unit
  tests since 2026-11-19; the listener itself ran in the virtual machine only).

The comparison of assertions is a review the operator may or may not want.

### 5. "`./scripts/check.sh` still passes for the Rune build."

**Met at the last commit that held the Rune build; it cannot be run again.**

The Rune build was removed at the cutover (commit `71d9119`). At the last commit before it,
`89d700c`, with both front ends in the tree, the whole script passed twice: in CI
([run 44426541137](https://github.com/z23/xenadmin-rs/actions/runs/44426541137), which runs
`./scripts/check.sh` and then builds the packages, then of the Rune client) and on the development
workstation with no display (`XENADMIN_TEST_TIME_SCALE=4`, exit status 0; the log is not in the
repository). From the cutover on, the script checks the GPUI front end only, and criterion 1 of
[gate G5](2026-11-19-gpui-gate-g5.md) takes this one's place.
