# vApp organization and ordered power controls

The Organize workspace now opens a vApp manager. Operators can create an empty group,
edit its name and description, add or remove existing ordinary VMs, edit each member's
order/start delay/shutdown delay, and delete an empty group. Removing membership or deleting
an empty group never deletes a VM or disk. Moving between groups requires an explicit removal
followed by a separately reviewed addition. Filters locate groups and VMs beyond the bounded
visible lists; reviews include UUIDs as well as names.

Start, clean shutdown and force shutdown are separate reviewed server-side group operations.
Start runs in ascending order; shutdown runs in descending order. Equal orders run together.
Already-target-state guests are skipped by XAPI. Start refuses paused or suspended guests
that need an individual recovery action. Clean shutdown never falls back to force shutdown.
Force shutdown requires the exact group UUID and explains guest data loss. Membership and
power reviews are bounded to 256 VMs, and each delay is limited to 86,400 seconds.

## Backend behavior

Typed commands reserve the pool through the resource journal. Every operation resolves group
and VM UUIDs afresh. Power preflight compares the exact member set, each member's power state,
order and delays, ordinary-VM identity and group membership, and idle group/VM task maps.
The group must advertise the operation, and each VM changing state passes the server's
operation-validity assertion. Membership and property setters check reviewed previous values
before dispatch. Multiple setters persist each dispatch and verification independently.

Asynchronous creation records an immutable pre-existing UUID baseline and task/result identity.
Creation is verified as a new, empty group; matching names never establish provenance. Group
power and deletion require a saved task-success receipt plus fresh state verification. Power
verification checks every member, its unchanged ordering, membership and idle state. Parent
task success with an unchanged child remains unknown. Failed or cancelled group tasks retain
the pool reservation because some guests may have changed already. Lost task replies are never
replayed; saved completion receipts allow read-only recovery after the task record disappears.
Public history exposes typed IDs and action descriptions, not RPC references.

Concurrent external clients can still change XAPI objects between preflight and dispatch; XAPI
has no transaction spanning these checks and a mutation. A resulting mismatch is retained for
inspection, not automatically compensated. The client does not run an independent scheduler.

## Verification

Ten new synthetic direct-XAPI fixtures cover creation identity and public history, membership,
ordering, empty deletion without guest deletion, start/clean-shutdown dispatch, changed
membership/order/VM kind, failed and cancelled tasks, lost replies, partial setters, read-only
admission, incomplete inventory, saved completion recovery, and parent success with an unchanged
child. A journal test checks that the baseline and completion receipt survive reload and cannot
be retracted. Three Rune interaction tests cover captured order, exact membership, force UUID
confirmation, compact controls and refusal of preview submission. Compact and wide synthetic
screens were visually inspected. Peer review added the immutable-baseline guard and the
unchanged-child fixture.

The isolated branch passed the workspace regression suite and strict Clippy. These are synthetic
checks; live XCP-ng group sequencing, delays and guest shutdown behavior await the prepared
local lab. Native accessibility qualification remains open. No private user screenshots or
inventories were used as test artifacts.
