# Activity, tasks, messages and local history

This increment implements the Activity workspace for P14-04, P14-05 and P14-10. It uses
existing direct XAPI connections and does not require Xen Orchestra. The evidence below
comes from synthetic protocol and Rune fixtures, not a live XCP-ng pool.

## Operator workflows

- Tasks lists pool-wide server tasks, including work submitted by other clients. Search
  matches name, description, UUID and displayed details; a separate filter matches status.
  Details include status, progress, creation/finish fields, error code, resident host,
  parent/subtask UUIDs and result type when the host supplies them. Raw result references,
  arbitrary error arguments and debug backtraces are not exposed.
- Cancellation requires a current writable connection, a reviewed typed task UUID and the
  host's advertised cancel operation. A fresh UUID/capability read precedes dispatch.
  The review captures the original pool and connection generation; selection changes
  cannot retarget it. Read-only profiles cannot dispatch cancellation.
- Messages lists typed pool messages and alerts, with text/UUID and priority filtering.
  Dismissal reviews one exact message and removes it from the server for all clients.
  The journal stores a digest of the reviewed content, not its body. Fresh content must
  match before `message.destroy` can be sent; a fresh absence check establishes removal.
  Dismissal does not resolve the underlying condition or change alarm configuration.
- History combines all local VM and resource operation kinds, preserves pool identities,
  and remains available after disconnect or a pool switch. Only terminal records can be
  hidden locally. Include hidden entries exposes a restore action. Hiding changes a private
  preference and leaves the durable operation journal intact. Unknown and active outcomes
  cannot be hidden, even if an old hidden preference names that record.
- Export uses Rune's native Save dialog and captures the filtered selection when opened.
  Subsequent pool, filter or window changes do not change that captured export. A background
  writer serializes an explicit versioned public projection, bounded to 32 MiB, then writes
  an owner-only regular file through an atomic temporary-file rename and sync. Existing
  symlink destinations are rejected. Exports include displayed message text and public
  operation details; private lifecycle plans, task/session references, raw RPC responses,
  credentials and action request payloads are not serialized.

Task/message inventory remains visible in memory after disconnect or switching pools;
its details identify cached/inactive views. Actions require the matching current connection.
Unavailable optional inventory classes remain explicit. Local history retains the existing
newest-100-terminal-plus-all-unresolved display bounds for each operation family; journal
retention remains unchanged. Hidden preferences are bounded to 5,000 identities.

## Cancellation and recovery semantics

The server's cancellation API requests cancellation and may finish normally, fail, or take
an arbitrary interval to stop. Status, not progress or the cancellation RPC reply, determines
the result. This follows the [primary task API](https://xapi-project.github.io/xen-api/classes/task.html).

The cancellation operation is journaled before dispatch. Its local reservation is narrowly
scoped to the task identity, so it can help recover a pool with an active or unknown mutation.
It does not acknowledge, release or replace the original mutation's reservation. Concurrent
cancellation attempts for the same task are rejected while its outcome is unresolved.

An accepted request with a pending task stays CancellationRequested; cancelling is also
nonterminal. A fresh cancelled status confirms cancellation. Success or failure of the
original task is reported as that different outcome, never as successful cancellation.
Lost replies remain unknown. Recheck and restart read existing task status without replaying
`task.cancel`. A missing task is not evidence that work stopped. The cancellation observer
never destroys the original task record; its creator retains ownership and reconciliation.

Message dismissal uses the longstanding single-message
[message.destroy API](https://xapi-project.github.io/xen-api/classes/message.html).
A lost reply is unresolved until a read establishes that the reviewed UUID is absent.
Recheck never repeats the deletion.

## Verification

- Eight synthetic direct-connection fixtures cover actual terminal cancellation states,
  pending/cancelling status, duplicate cancellation, original local task reconciliation,
  changed UUID/capability/message content, lost replies, restart without replay, message
  absence verification, read-only mode and superseded generations.
- A journal regression proves the cancellation exception preserves the original unknown
  VM reservation, rejects duplicate task cancellation, and does not block unrelated VMs.
- Six Rune tests cover compact/wide review controls, captured task/message targets, stale
  and synthetic dispatch refusal, filtering and pool switches, terminal-only hide/restore,
  explicit export projection, native Save cancellation, captured payloads, 0600 permissions
  and symlink refusal.
- The full workspace suite passed **254 tests**: 124 core unit, 49 direct protocol, five
  profile, four TLS, four host-probe and 68 desktop tests. Strict workspace Clippy, formatting
  and diff whitespace checks passed.
- The synthetic `--scene activity` rendered at 1440×900 and 513×652 with Rune's Vulkan
  backend. Both images were visually inspected locally. The compact view scrolls to details
  and actions; fixture interaction tests reached its review and close controls.

No host mutation, private inventory export or user screenshot publication was performed.
Real Wayland/X11 save portals, keyboard/screen-reader behavior and host-specific task/event
compatibility remain lab/native qualification work. This increment does not implement alarm
thresholds, email notification settings, general resource reports, support bundles or broader
metrics work. P14-11 and the broader P14-12 report scope remain open.
